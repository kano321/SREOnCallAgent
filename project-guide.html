01这个项目是干什么的

凌晨 3 点生产告警响起，值班工程师要手动完成一整套重复劳动。这个项目把同样的流程交给智能体流水线，人只负责看结论、做决策。

传统值班：人工排障
1
收到告警，打开日志平台凭经验猜该先查什么
2
翻日志找错误模式关键词全靠试，容易漏
3
切到监控查指标趋势日志和指标两边来回切换
4
翻 Runbook 找处置步骤文档散落，现场紧张容易跳步
5
手工写复盘报告格式随意，质量看心情
全程约 30~60 分钟，质量依赖个人经验
本项目：智能体流水线
1
TriageAgent 读取告警 JSON自动生成 4~6 步有序调查计划
2
InvestigationAgent 循环取证按计划调用日志/指标/Runbook 三个工具
3
证据逐步收敛到根因每一步 Thought/Action/Observation 都记录
4
PostmortemAgent 起草 RCA 报告7 节标准结构：时间线、5-Whys、行动项...
5
自评审打分，不达标自动修订存入 MySQL，历史随时可查
分钟级完成，过程全程可视化，方法论一致
一句话：它不是「让 AI 编答案」，而是把资深 SRE 的排障方法论（先看什么、再查什么、证据如何收敛）固化成可自动执行、可审计的流水线。

03技术栈地图：每层用了什么、为什么

鼠标悬停任意技术项，可以看到它在项目里的具体用途和选型原因。

前端层Frontend
原生 HTML/CSS/JS零依赖、零构建，打开即用；顺便手写了一个迷你 Markdown 渲染器来展示复盘报告 EventSource (SSE)浏览器原生支持流式接收，每收到一个事件就追加一张 Thought / Action / Observation 卡片 并发事故卡片多个事故同时调查，各自独立卡片 + 进度条 + 最小化，互不干扰 no-store 缓存策略页面和静态资源禁用浏览器缓存，功能更新立即可见
API 层FastAPI
FastAPI + Uvicorn异步高性能框架；SSE 端点用 StreamingResponse 持续推送流水线事件 Bearer Token 认证登录签发 Token，中间件统一校验，登出即吊销 PBKDF2 加盐哈希用户密码不落明文，找回密码用自定义安全问题 CORS前后端分离开发时允许跨域调用
智能体层3 Paradigms
TriageAgent · Plan-and-Solve先规划后执行：LLM 把告警转成 4~6 步调查计划，每步绑定一个工具和查询词 InvestigationAgent · ReActReason + Act 循环：Thought 推理 → Action 调工具 → Observation 看结果 → 修正假设，直到 Finish PostmortemAgent · Reflection草稿 → 按 5 条质量标准自评审打分 → 低于 8 分自动修订后再评 emit 事件回调三个 Agent 都接受统一的 emit 回调，把每个动作实时上报给流水线，再推给前端
工具层Tools
log_search按关键词或正则检索事故日志；正则非法时自动降级为普通子串匹配，不会崩 metric_query按时序指标名模糊匹配，返回随时间变化的数值序列，用于验证假设趋势 runbook_lookup按服务名加载 YAML Runbook，按错误模式匹配处置步骤；找不到精确匹配就返回全部步骤兜底
LLM 层Client
OpenAI 兼容客户端统一封装 chat.completions 调用，一套代码可切换 DeepSeek / AIHubmix / Qwen / OpenAI 流式输出stream=True 逐 token 接收，控制台实时可见，也便于后续接前端 temperature=0排障场景要确定性输出，温度归零减少随机性，方便格式解析 .env 配置模型、密钥、地址全走环境变量，换供应商不改代码
数据层Storage
MySQL (PyMySQL)存用户、Token、历史报告；启动时自动建库建表；支持报告搜索与批量清理 事故 JSON每个故障样例一个文件：告警元数据 + 日志条目 + 时序指标 + 标准根因 Runbook YAML按服务组织的标准处置手册，错误模式 → 严重级别 → 有序修复步骤
